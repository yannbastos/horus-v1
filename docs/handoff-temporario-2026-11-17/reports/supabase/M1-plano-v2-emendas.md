## 2. Emendas de semântica e segurança (M1 §§4–8)

**A1 — consumo:** UoW READ COMMITTED adquire advisory xact por (action,subject), também usado por grant; ordem global: orçamento Hermes→raiz workflow/job→checkpoint. Ler `t` do relógio PG **depois da espera de lock**, nunca relógio do Windows; antes de UPDATE reler relógio para não consumir após expirar durante espera/processamento. SQL parametrizado, em uma conexão, sem rede externa:
```sql
SELECT * FROM horus.human_checkpoints
 WHERE action=%(action)s AND subject=%(subject)s
   AND consumed_at IS NULL AND expires_at>%(t)s
 ORDER BY seq DESC LIMIT 1 FOR UPDATE;
-- validar limit_amount/currency na linha escolhida; então atualizar somente seu id:
UPDATE horus.human_checkpoints
 SET consumed_at=%(t_final)s, consumed_ref=%(ref)s
 WHERE id=%(id)s AND consumed_at IS NULL AND expires_at>%(t_final)s
   AND (%(amount)s::numeric IS NULL OR
        (limit_amount IS NOT NULL AND currency=%(currency)s
         AND %(amount)s::numeric<=limit_amount))
 RETURNING *;
```
Não filtrar amount/currency no SELECT: se o último checkpoint válido tem limite insuficiente, recusar; não buscar um anterior mais permissivo. Se não há candidato, consultar existência sob mesmo lock: nenhuma linha→checkpoint_missing; nenhuma não consumida→checkpoint_consumed; não consumidas todas expiradas→checkpoint_expired. Amount informado exige Decimal finito/não negativo, limite presente/moeda exata/amount<=limite; falha→checkpoint_limit_exceeded, sem consumo. Amount ausente preserva publicação sem teto. UPDATE sem retorno por expiração gera checkpoint_expired; demais conflitos reavaliados sem inventar sucesso. Trigger consume_once e recibo/intenção na mesma UoW; um vencedor **por linha**, não proibir duas aprovações distintas legítimas. Não usar SKIP LOCKED. Ref até 120 caracteres e auditoria da recusa somente após rollback, como hoje.
ClockProvider interno único: produção faz SELECT clock_timestamp(); grant/consume/orçamento usam o mesmo provedor. Testes injetam instante UTC **só no harness**, como self.clock atual (test_human_checkpoints.py:42/161/194); nenhum parâmetro HTTP/GUC aceito do usuário altera relógio. Testar empate temporal/seq, último expirado com anterior válido, último válido com limite insuficiente, moedas, fronteira de expiração e duas sessões/um checkpoint.

## 3. Contrato HTTP FINAL para I1 e M2 (substitui o provisório)

Ainda **não implementado**. Todos endpoints exigem autenticação local/origem/Host permitidos; Cache-Control:no-store, sem request-body/DSN/SQL/usuário/senha nos logs/respostas/erros; validation error sanitizado não inclui input. Não fornecer endpoint que leia credencial. Estado inicial vem de consulta real ao cofre: entrada ausente→not_configured; exceção/backend inseguro ou falha de leitura/escrita/exclusão→vault_unavailable. Cofre indisponível nunca equivale a senha vazia.

| Campo de DatabaseStatus (JSON, todos obrigatórios) | Tipo / semântica |
|---|---|
| state | enum not_configured, connecting, connected, unreachable, auth_failed, schema_mismatch, migrating, **vault_unavailable** |
| latency_ms | number>=0 ou null; RTT da última verificação completa bem-sucedida, não duração de falha; null enquanto não connected |
| schema_version | string ou null; versão do ledger lida; sem ledger→null, incompatibilidade→schema_mismatch |
| expected_schema_version | string não vazia; versão exigida pelo app, mesmo sem conexão |
| last_error_code | código estável abaixo ou null; connected/not_configured/connecting/migrating sem falha→null; não mensagem livre |
| host_label | string sanitizada ou null; rótulo fixo “Supabase (sessão 5432)” quando configurado, null sem configuração; sem hostname real/user/database/DSN |
| checked_at | string RFC3339 UTC com Z ou null; término da última tentativa, null antes da primeira; não muda em GET de cache |

| Endpoint | Pedido exato | Resposta / efeitos |
|---|---|---|
| GET /v1/database/status | Sem body | **200 DatabaseStatus**, inclusive falha do banco/cofre; snapshot cacheado, não cria conexão em cada poll |
| POST /v1/database/connection | JSON {host:string,port:integer,database:string,user:string,password:string}; seis obrigatórios, extra proibido; port=5432 neste corte | **200 DatabaseStatus** após salvar com segurança e verificar em tempo limitado; 200 significa configuração persistida, não conexão pronta: UI usa state. Pode retornar auth_failed/unreachable/schema_mismatch/migrating; jamais connected sem validações |
| DELETE /v1/database/connection | Sem body | **200 DatabaseStatus** com not_configured após fechar pool/coordenação e remover segredo+metadados; idempotente; não revoga senha remota, não apaga dados PG |
| POST /v1/database/test | Sem body ({} aceito); nenhum host/user/password | **200 DatabaseStatus** após teste limitado da configuração **já salva**; não salva/altera segredo nem migra schema; ausente→not_configured, cofre falha→vault_unavailable. Testar candidato exige POST connection |

POST connection muda a ordem do M1: validar **sintaxe/destino**, persistir segredo e descritor juntos em entrada keyring versionada, conferir releitura sem log, depois testar conexão. Isso permite configurar uma vez mesmo com internet indisponível; falha de BD fica em state. Limites: body até 16KiB; host<=253, database/user<=128, password<=4096 caracteres, strings não vazias; sem trim/truncamento da senha; aceitar caracteres especiais como dados parametrizados, nunca concatenação em DSN. Host/porta/database/user passam whitelist/validação do backend; só horus_app com sufixo tenant esperado no pooler, sem postgres/service_role. Sem autofill de senha salva; UI apaga campo após envio, nunca localStorage.
Troca/DELETE são serializadas e recusadas **antes de alteração** se produção/job ativo ou migração/reserva de update; HTTP409/database_busy. Esse bloqueio considera processos locais efetivamente ativos, não jobs queued remotos; em auth_failed/vault_unavailable, reparo continua possível após parada/quiescência local verificada, sem exigir leitura PG indisponível. Após admissão, bloquear checkout novo, drenar UoWs curtas com prazo, invalidar fencing/coordenação e **fechar pool antigo**; criar ConnectionPool novo com geração de credencial nova, validar TLS/papel/schema antes de liberar. Sem reaproveitar conexões autenticadas com senha antiga nem fallback automático ao segredo anterior. Falha de keyring fecha pools/limpa credencial em memória e retorna vault_unavailable; não operar só com senha do formulário/cache. Senha rotacionada fora do app pode deixar sessões antigas válidas: ao primeiro 28P01/28000 invalidar geração inteira/fechar pool e auth_failed, não retry infinito; POST com senha nova recria pool. Nenhum login/senha é rotacionado remotamente por estes endpoints.

Auth local existente preserva seus HTTP401/403 e formato atual (api.py:170–179); UI trata por HTTP antes do envelope. POST/test retornam connecting somente se tentativa concorrente já está em curso (deduplicada), com verificação limitada continuando no backend; nenhum retry/poll sem limite. Estado connected só se versão/papel/TLS/lease exigido estiverem válidos; migrating mostra manutenção sem permitir escrita. Na API operacional, falha de BD/cofre→HTTP503 com mesmo código estável e envelope detail sanitizado, sem fallback SQLite.
